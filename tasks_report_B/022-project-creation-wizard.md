## Decisions Made
- **Prompt conflict resolved as 022:** the heading said 022-project-creation-wizard while `TARGET_TASK_FILE` still pointed at `021-project-list.md`; 021’s report already exists as COMPLETED, so the stale file pointer was treated as a copy-paste error and 022 executed (this documents the call).
- **Payload via narrow cast, not PATCH-after-create:** the bundle types `ProjectCreateRequest` as name/source/target only, but the Task 007 controller accepts `description` + `processingSettings` (folded into the server hash). A single POST carries them via a documented cast at one call site (021’s precedent); a create-then-PATCH would bump the version, need If-Match handling, and contradict “Start → POST /projects”.
- **Hash preview honesty:** the client shows an FNV-1a preview explicitly labeled as such; the server SHA-256 on the created project stays authoritative. No `SubtleCrypto` async surface — tests stay hermetic.
- **Upload is a seam, not an engine:** attach-now records metadata + in-memory `File` (re-attach required after refresh by design); the transfer itself belongs to Task 023, so deferred creation lands on the `/media` deep link where that uploader will live (today a placeholder shell renders — asserted as details+URL in E2E).
- **No permission gate on the wizard route:** the server re-authorizes (`RequireProjectEditor`); the *entry links* are `project.edit`-hinted per valid-actions-only, but the form itself stays reachable so 403s surface as mapped form errors rather than dead ends.
- **R5 gate excludes import lines:** shared seams live under `app/providers/*`, so the source scan strips import statements — only rendered inputs/fields can fail it.
- **Client requires the name though the backend defaults it:** R1’s “enforced client- and server-side” means the wizard blocks empty names locally and maps any server 400 back to fields; the backend’s absent→Untitled compatibility is untouched.

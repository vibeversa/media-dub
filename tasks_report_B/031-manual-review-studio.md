## Decisions Made
- **Hardened mapping approve→resolve etc.:** legacy `approve/reject/requeue` carry no body so cannot satisfy R2 (key+version+reason); studio maps UX labels to hardened `resolve/dismiss/reopen/resolve-with-edit` per Task 011 `ReviewMutationService` (resolve→Approve, dismiss→Reject, reopen→Requeue). Documented in `useDisposition.ts` header and `dispositionEndpointFor`.
- **Optional reason fallback:** backend requires reason for all hardened calls but Task 031 says reject/requeue required, others optional; `buildDispositionPayload` sends neutral `"Approved via review studio."`/`"Reviewed via review studio."` when optional note empty, so UI stays optional while backend never 400s. Required validation only for reject/requeue via `validateReason`.
- **Client-side 500-char gate:** backend truncates overlong reasons but Task 031 edge case demands 400 inline without send; `validateReason` blocks send and shows `review-field-error` (test asserts zero mutation calls). `maxLength` on textarea allows typing past limit to trigger the gate.
- **Stable key lifecycle:** `dispositionKeyFor(reviewId,action)` stable until success; `FailAsync` on backend failures releases the claim so same-key retry with refreshed `expectedVersion` succeeds (no `IDEMPOTENCY_KEY_REUSED`); `rotateDispositionKey` on success gives next intent a fresh key. `resetDispositionKeysForTests` for hermetic tests.
- **Project filter via path:** `GET /projects/{id}/reviews` has no cross-project list; `toReviewListQuery` omits `project` from query (path owns it) while `ReviewStudio` owns `project` in URL (`?project=prj_1`) and passes it as `projectId` prop — R1 "project narrows server-side" satisfied by path, other six by query params.
- **Queue key extension not new scope:** extended `queryKeys.review.list` with `ReviewListParams` instead of new `queryKeys.reviews` scope (task wording) to keep `keysForEvent('review.*')` invalidation and R1 scan green; key includes filters via `withDefaults` spread.
- **History from context aggregate:** no separate history endpoint exists in bundle; `useReviewContext` parses `history[]` from `GET /reviews/{id}/context` and sorts newest-first via `sortHistoryNewestFirst`; pending spinner row while `disposition.isPending`.
